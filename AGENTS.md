# AGENTS.md — Repository Operating Rules

These instructions apply to the entire repository unless a deeper `AGENTS.md`
overrides them for a narrower directory.

## 1. Mission

Evolve the implemented Vietnamese-English evaluation toolkit and synthetic
portfolio into a professional, reproducible evaluation lab. Every change must
strengthen at least one of:

1. construct validity;
2. benchmark quality;
3. annotation reliability;
4. calibration and uncertainty;
5. experiment reproducibility;
6. code or agent evaluation rigor;
7. security and auditability;
8. reviewer-verifiable evidence.

Do not optimize for lines of code, file count, test count, badges, or UI
appearance in isolation.

## 2. Status vocabulary

Use these labels consistently:

- **CURRENT / IMPLEMENTED:** present in repository code or data and verifiable
  with a documented check.
- **TARGET / PLANNED:** an approved design or roadmap direction that is not yet
  a repository capability.
- **NOT YET IMPLEMENTED:** explicitly absent from the current baseline.

Governance or design documentation does not by itself make a capability
implemented. Never call this repository production-ready unless every
applicable release gate in
[`docs/12_DEFINITION_OF_DONE.md`](docs/12_DEFINITION_OF_DONE.md) is satisfied.

## 3. Mandatory reading before work

Before modifying code or project behavior, read:

1. [`CODEX_MASTER_CONTEXT.md`](CODEX_MASTER_CONTEXT.md)
2. [`docs/00_PROJECT_CHARTER.md`](docs/00_PROJECT_CHARTER.md)
3. [`docs/01_TARGET_ARCHITECTURE.md`](docs/01_TARGET_ARCHITECTURE.md)
4. the active milestone in
   [`docs/02_ROADMAP_24_WEEKS.md`](docs/02_ROADMAP_24_WEEKS.md)
5. the assigned issue in [`planning/BACKLOG.md`](planning/BACKLOG.md)
6. relevant methodology and security documents

Inspect the current repository, Git status, tests, and relevant history. Do not
assume a planned capability has already landed.

## 4. Task scope

- Work on one issue or one tightly coupled vertical slice per pull request.
- Do not perform a big-bang rewrite.
- Preserve current public samples and backwards compatibility until a
  migration is tested and documented.
- Avoid unrelated cleanup.
- Split an issue before implementation if it cannot remain reviewable.
- Record material architecture choices as ADRs.

## 5. Truthfulness and claims

- Never fabricate metrics, benchmark sizes, agreement scores, coverage,
  performance, costs, model results, or production readiness.
- A README, CV-facing, or portfolio claim must resolve to repository evidence.
- Label simulated, synthetic, mocked, pilot, experimental, and production data
  accurately.
- Do not infer paid technical-evaluation experience from independent projects.
- Static counts should identify their commit/version or be generated by a
  reproducible command.

## 6. Confidentiality and data policy

- Never add content from private paid AI platforms or clients, including
  prompts, outputs, screenshots, rubrics, guidelines, project names, queue
  metadata, private repositories, or internal instructions.
- Use original synthetic samples, permissively licensed public data, or data
  explicitly created for this repository.
- Record provenance and license where a dataset or benchmark is introduced.
- Remove secrets, personal data, hidden identifiers, and credentials.
- Paid experience may inform general skill categories, never copied content or
  implied affiliation.

See [`docs/10_DATA_GOVERNANCE_NDA.md`](docs/10_DATA_GOVERNANCE_NDA.md).

## 7. Architecture rules

These are target constraints for future implementation:

- Keep the core vendor-neutral.
- Put provider integrations behind adapters.
- External evaluation frameworks may be optional adapters; none becomes the
  domain model.
- Separate domain records, registries, evaluators, experiments, metrics,
  annotations/adjudication, sandboxes, reports, and UI.
- Prefer dependency inversion and typed protocols over provider conditionals.
- Stabilize CLI and library APIs before UI.
- Do not introduce a service database until file/SQLite storage is shown to be
  insufficient.

Do not rename the current `src.*` package or introduce the target layout outside
the issue that owns that migration.

## 8. Evaluation-method rules

Future evaluation records and systems must:

- store scores for each response, not only the selected winner;
- separate deterministic checks from model-graded and human judgments;
- blind model identity where possible;
- randomize pair order and support swap tests;
- preserve item-level results;
- report slices, uncertainty, and limitations;
- version/hash datasets, rubrics, prompts, configs, and sandbox images;
- evaluate a judge on a separate calibration set;
- support escalation for low-confidence or policy-sensitive cases.

These requirements are planned standards, not claims about the current schema.

## 9. Benchmark and annotation rules

Every future benchmark item requires stable identity, task/language metadata,
input and candidate/target data, provenance/license, rubric version, evidence
or executable oracle where applicable, slice/difficulty tags, contamination
risk, review/gold status, and change history.

Annotation pilots require independent first-pass labels. Annotators must not
see peer labels before submission. Store confidence separately from labels.
Preserve disagreements and all original labels during adjudication. Choose
agreement statistics for the actual scale and annotation design.

## 10. Code and agent execution safety

The current code checks parse syntax and structured text only. They are not a
sandbox.

When restricted execution is implemented under its assigned issues, default
controls must include no outbound network, non-root execution, read-only root
where practical, an isolated writable workspace, CPU/memory/process/disk/time
limits, a pinned image digest, no Docker socket or host credentials, allowlisted
tools, complete results, and cleanup on timeout/exception.

Any relaxation requires an ADR and explicit human approval. Never run
untrusted generated code directly on the host.

## 11. Engineering standards

The current required checks are the checks present in the repository:

```bash
python -m pytest -q
python -m src.jsonl_validator data/sample_prompts.jsonl --schema prompt
python -m src.jsonl_validator data/sample_responses.jsonl --schema response
python -m src.jsonl_validator data/sample_evaluations.jsonl --schema evaluation
```

After their corresponding setup issues land, target checks include Ruff, mypy,
coverage, pre-commit, and dependency auditing. Do not claim or require those
tools before they are installed and documented.

Additional rules:

- Python 3.12 is the CI baseline unless an ADR changes it.
- Public functions and domain models require type hints and docstrings.
- Deterministic tests must not require network or paid APIs.
- External-model tests must be opt-in and clearly marked.
- Use fixed fixtures and seeded randomness.
- Add negative, boundary, migration, and failure-path tests.
- Verify behavior rather than implementation details.
- Never lower a quality gate solely to make a change pass.

## 12. Dependency policy

A new dependency requires:

- the problem it solves;
- alternatives considered;
- maintenance/security assessment;
- license;
- core/optional/dev/adapter classification;
- a test demonstrating its use.

Prefer the standard library and focused dependencies.

## 13. Git and pull-request discipline

- Use conventional commits.
- Keep commits reviewable and linked to one backlog issue.
- Update [`CHANGELOG.md`](CHANGELOG.md) for notable changes.
- Update affected documentation in the same pull request.
- Include migration notes for schema or CLI changes.
- Never commit secrets, caches, local databases, private model responses, or
  large generated artifacts.
- Do not rewrite shared history.

The active pull-request template is
[`.github/pull_request_template.md`](.github/pull_request_template.md).

## 14. Required completion report

Every completed task must report:

1. issue and scope;
2. branch and Git root;
3. architecture/reconcile decision;
4. files changed;
5. checks run with exact results;
6. evidence or artifacts;
7. compatibility/migration impact;
8. security/privacy/NDA impact;
9. known limitations;
10. Git diff summary;
11. acceptance-criteria status;
12. next recommended issue.

If a required check cannot run, state exactly why. Do not say “all good”
without evidence.

## 15. Stop conditions

Stop and request human review when:

- an action risks exposing private platform/client data;
- the task requires weakening sandbox or network restrictions;
- a benchmark construct or gold answer is ambiguous;
- a schema migration could destroy user data;
- a public claim lacks evidence;
- a security-sensitive design has multiple plausible threat models;
- acceptance criteria conflict with repository reality.

For ordinary implementation ambiguity, make the smallest reversible,
well-documented in-scope choice.
