# 24-Week Roadmap

> Status: TARGET / PLANNED sequencing. Weeks are sequencing units, not claims
> of elapsed work or implemented capability.

## Work model

- Approximately 12–15 focused hours/week.
- One main implementation issue and one documentation/quality issue at a time.
- End each phase with evidence and a release only when its gate is met.
- Preserve a working default branch.
- Never pass a gate with missing evidence.

## Phase 0 — Baseline and governance (Weeks 1–2)

### Week 1: Freeze and measure the current state

Deliver:

- durable repository instructions and project documents;
- baseline architecture and repository inventory;
- current schema/CLI behavior snapshots;
- test/data counts generated by script;
- current claim-evidence matrix;
- changelog, ADR directory, contribution and security documents;
- baseline tag after all gates pass.

Acceptance:

- clean install and tests documented;
- current JSONL validates;
- README claims map to evidence or are marked unsupported;
- generated facts are not maintained as unaudited manual numbers.

### Week 2: Packaging and quality foundation

Deliver:

- `pyproject.toml`;
- dependency groups;
- Ruff, mypy, coverage, and pre-commit;
- deterministic CI matrix;
- test/coverage/baseline report artifacts;
- documented development commands.

Gate M0:

- current behavior preserved;
- CI green;
- baseline report reproducible from a clean checkout.

## Phase 1 — Evaluation Core v2 (Weeks 3–6)

### Week 3: Domain schema v2

Implement versioned benchmark/rubric/candidate/annotation/adjudication/run IDs,
per-response criterion scores, `A`/`B`/`Tie`/`BothBad`, evidence, confidence,
dataset/rubric versions, and immutable model configuration.

Acceptance:

- round-trip serialization;
- strict extra-field policy;
- compatibility reader for current records;
- schema export.

### Week 4: Dataset and rubric manifests

Implement split/provenance/license manifests, SHA-256 hashes, rubric scale/hard
constraint models, and semantic-version validation.

Acceptance:

- source changes alter the benchmark hash;
- reports identify exact dataset/rubric identity;
- invalid references fail with useful diagnostics.

### Week 5: Cross-record integrity and migration

Check missing/mismatched/orphan/duplicate records, impossible evidence spans,
winner/score contradictions, and provide a non-destructive legacy migration.

Acceptance:

- migration is idempotent;
- original files are not overwritten by default;
- every error class has a failure fixture.

### Week 6: Stable library and CLI

Implement typed validate, inspect, migrate, and export services with stable exit
codes and machine-readable output.

Gate M1 / target release `v0.2.0`:

- v2 records work end-to-end;
- current samples migrate;
- architecture/ADRs are current;
- no UI dependency.

## Phase 2 — Benchmark and Human Operations (Weeks 7–10)

### Week 7: Benchmark design

Create benchmark/data card templates, authoring and defect review, difficulty
and slice taxonomy, contamination policy, and an original 20-item VI-EN pilot
with ties, both-bad outcomes, trade-offs, and evidence.

### Week 8: Annotation workflow

Implement blinded/randomized assignment, independent submission, confidence,
evidence, duration, import/export, and qualification mode.

### Week 9: Disagreement and adjudication

Implement disagreement taxonomy, queues, immutable adjudication records, and
guideline/item-defect flags without mutating original labels.

### Week 10: Agreement and pilot revision

Implement raw agreement, appropriate kappa/alpha support, slice reports, and
bootstrap intervals where appropriate. Run a pilot, revise, and recheck a
holdout.

Gate M2 / target release `v0.3.0`:

- methodology and limitations are public;
- any simulated labels are labeled simulated;
- no multi-human-study claim without multiple humans;
- disagreement and adjudication are auditable.

## Phase 3 — Calibration and Experiment Engine (Weeks 11–15)

### Week 11: Experiment manifest and target protocol

Implement a provider-neutral target, mock/replay target, complete config
identity, resumable item states, and raw output/trace persistence.

### Week 12: Evaluators

Implement exact/schema/constraint graders, typed results, hard failures,
versioning, diagnostics, and reproducible grading from saved outputs.

### Week 13: Paired comparison and uncertainty

Implement baseline/candidate pairing, order randomization, slices, paired
bootstrap intervals, practical thresholds, and explicit incomplete-item policy.

### Week 14: Judge calibration

Implement an optional model-judge adapter, blinding/swap and perturbation
probes, confidence/calibration metrics, abstention/escalation, latency, and
cost.

### Week 15: Reports and regression CI

Deliver immutable JSON results, CSV/Markdown/HTML rendering, baseline pinning,
deterministic smoke benchmarks, and failure artifacts.

Gate M3 / target release `v0.4.0`:

- baseline/candidate experiment demonstrated;
- uncertainty and slices reported;
- judge limitations published;
- CI requires no external provider.

## Phase 4 — Production-Style Code Evaluation (Weeks 16–19)

### Week 16: Threat model and sandbox

Implement the sandbox protocol and reviewed backend with no network, non-root
execution, read-only root where practical, isolated workspace, resource/time
limits, logs, cleanup, and image identity.

### Week 17: Python benchmark

Add function and repository-task prototypes with public/hidden/property tests,
gold validation, and scope/security checks.

### Week 18: JavaScript/TypeScript and SQL

Add pinned Vitest and disposable PostgreSQL fixtures only after the sandbox
boundary is established.

### Week 19: Audit and reporting

Report patch/parse/build/test/regression/security/resource/scope results and
document task defects and flakiness.

Gate M4 / target release `v0.5.0`:

- at least one audited slice per supported language;
- reproducible restricted-execution report;
- no host secret or network exposure.

## Phase 5 — Agent Evaluation (Weeks 20–22)

### Week 20: Trace and controlled tools

Implement messages/tools/state/approval/error events, deterministic local
fixtures, trace hashing, persistence, and replay.

### Week 21: Outcome and trajectory scoring

Implement final-state, tool-choice/argument/order/recovery, unnecessary-action,
policy, cost/latency, and step metrics with trace evidence.

### Week 22: Agent challenge suite

Create offline tasks for multi-turn constraints, tool failure, repository edits,
fixed-corpus research, approvals, conflicting instructions, and safe
escalation.

Gate M5 / target release `v0.6.0`:

- agent configurations can be compared;
- outcome and trajectory remain separate;
- experimental scanners are labeled and limited.

## Phase 6 — Hardening, UI, and Public v1 (Weeks 23–24)

### Week 23: Hardening and reviewer experience

Review security, dependencies/licenses, performance, architecture, reviewer
navigation, claim evidence, and stable sample artifacts. A minimal UI may be
added only as a consumer of stable APIs.

### Week 24: Independent audit

Run fresh-clone installation, checks, benchmark validation, experiment
reproduction, restricted code execution, agent replay, link/claim/security and
limitations review.

Gate M6/M7 / target release `v1.0.0`:

- signed/tagged release;
- current changelog/cards/limitations;
- reproducibility evidence;
- CV wording derived only from verified artifacts.

## Accelerated variant

A 16–18 week sequence may parallelize independent implementation and
documentation. It must not remove gates or parallelize code against an
unsettled schema without a written interface contract.
